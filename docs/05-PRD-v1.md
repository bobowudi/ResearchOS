# ResearchOS — 第一版产品需求文档 (PRD v1)

> 多源证据驱动的 AI 调研决策系统

## 一、产品愿景

让每一个商业决策都有据可依、有迹可循、有果可验。

ResearchOS 不是又一个 BI 看板，也不是又一个问卷平台。它是一个把散落在问卷、访谈、舆情、行业报告中的碎片证据，通过 AI 对抗性推理，转化为结构化决策建议并追踪执行结果的闭环系统。

## 二、核心问题

| 痛点 | 现状 | ResearchOS 的解法 |
|------|------|-------------------|
| 证据碎片化 | 问卷在 A 系统、舆情在 B 系统、报告在 C 系统 | 多源证据统一汇聚，语义级对齐 |
| 洞察到行动断裂 | 研究团队出报告，决策者不知道该做什么 | 自动生成决策卡 + 行动项 |
| 决策缺乏闭环 | 做了决策没有追踪，不知道对不对 | 行动追踪 + 结果回看 + 模型校正 |
| AI 只说好话 | 现有 AI 工具倾向给出单一正面结论 | 对抗性推理引擎，主动呈现反面证据 |
| 研究资产沉睡 | 大量研究成果沉睡在 PPT/PDF 中 | 知识沉淀 + 证据复用 + 模式库 |

## 三、目标用户与场景

### 主要用户

| 角色 | 核心诉求 | 典型场景 |
|------|---------|---------|
| 品牌/市场负责人 | 基于多源数据做品牌决策 | 品牌定位、传播策略、竞品应对 |
| 产品经理 | 基于用户研究做产品决策 | 功能优先级、用户体验优化 |
| 研究/洞察团队 | 提升研究成果的影响力 | 研究项目管理、知识沉淀 |
| 企业高管 | 快速获取决策依据 | 战略规划、投资决策 |

### MVP 试点场景

**品牌健康度决策** — 数据源天然多样（NPS + 社媒口碑 + 竞品动态），决策频率适中（月度/季度），与现有 SaaS 问卷能力天然衔接。

## 四、核心价值链

```
决策 → 认知 → 洞察 → 行动 → 回看
```

不是传统的 `数据 → 图表 → 报告`，而是：

- **决策**：明确当前要解决的经营问题（Issue）
- **认知**：汇集多源证据形成结构化认知（Evidence → Decision Card）
- **洞察**：AI 对抗性推理发现证据中的模式、冲突和盲区
- **行动**：输出可执行的行动项（Action Item）
- **回看**：追踪行动结果，形成闭环学习（Review Result）

## 五、核心亮点功能：对抗性证据推理引擎

> 这是 ResearchOS 区别于所有竞品的杀手级能力。

### 问题

现有 AI 工具（Perplexity、ChatGPT、Elicit）在回答问题时倾向于给出单一结论，不主动呈现反面证据，不质疑数据质量，不识别信息盲区。这对于严肃的商业决策是危险的。

### 解法：三角对抗推理

当用户提出一个决策议题时，系统不是简单地汇总证据给出结论，而是启动三个独立的 AI Agent 进行对抗性推理：

```
用户提出议题："是否应该进入下沉市场？"
                    │
                    ▼
        ┌───────────────────────┐
        │   证据检索 & 聚合      │
        │   (RAG + 多源融合)     │
        └───────────┬───────────┘
                    │
          ┌─────────┴─────────┐
          ▼                   ▼
   ┌─────────────┐    ┌─────────────┐
   │  正方 Agent   │    │  反方 Agent   │
   │  (Advocate)  │    │  (Critic)    │
   │              │    │              │
   │ • 构建支持论证 │    │ • 构建反对论证 │
   │ • 寻找支撑证据 │    │ • 寻找反驳证据 │
   │ • 评估正面影响 │    │ • 识别逻辑漏洞 │
   │ • 列举成功案例 │    │ • 质疑数据质量 │
   └──────┬──────┘    └──────┬──────┘
          │                   │
          └─────────┬─────────┘
                    ▼
        ┌───────────────────────┐
        │   裁判 Agent (Judge)   │
        │                       │
        │ • 评估双方论证质量      │
        │ • 标注证据强度差异      │
        │ • 识别信息盲区         │
        │ • 生成平衡决策卡       │
        │ • 给出置信度评分       │
        └───────────────────────┘
```

### 用户看到的效果

一张决策卡包含：

| 区域 | 内容 |
|------|------|
| 决策建议 | 基于证据权衡后的推荐方向 |
| 支持证据 | 正方 Agent 找到的关键支撑，标注来源和强度 |
| 反对证据 | 反方 Agent 找到的关键反驳，标注来源和强度 |
| 证据冲突 | 同一维度上不同数据源的矛盾之处 |
| 信息盲区 | 当前证据未覆盖但对决策重要的领域 |
| 置信度 | 综合评分（高/中/低）+ 影响置信度的关键因素 |
| 前提假设 | 该建议成立的前提条件 |
| 失败预警 | "如果这个决策失败，最可能的原因是..." |

### 为什么这是护城河

1. **竞品不做**：Perplexity/Elicit 定位是"回答问题"，不是"辅助决策"，它们不会主动唱反调
2. **用户信任**：主动呈现反面证据和盲区，反而增强用户对系统的信任
3. **Prompt 体系壁垒**：三角推理的 prompt 设计需要大量领域迭代，不是简单复制架构就能复制效果
4. **数据飞轮**：每次用户采纳/拒绝决策卡的反馈，都在优化推理质量

## 七、核心对象模型

系统围绕 5 个核心对象运转，形成完整的决策生命周期：

```
Issue（议题）
  │
  │ 1:N
  ▼
Evidence（证据）
  │  ┌─ source: 问卷/舆情/竞品/报告
  │  ├─ stance: 支持/反对/中立
  │  ├─ confidence: 置信度评分
  │  └─ freshness: 时效性标记
  │
  │ N:M (聚合+推理)
  ▼
Decision Card（决策卡）
  │  ┌─ recommendation: 推荐方向
  │  ├─ pro_evidence: 支持证据集
  │  ├─ con_evidence: 反对证据集
  │  ├─ conflicts: 冲突点列表
  │  ├─ blind_spots: 信息盲区
  │  ├─ confidence_score: 综合置信度
  │  ├─ assumptions: 前提假设
  │  ├─ failure_warning: 失败预警
  │  └─ status: 待审阅/已采纳/已拒绝/已过期
  │
  │ 1:N
  ▼
Action Item（行动项）
  │  ┌─ owner: 责任人
  │  ├─ deadline: 截止日期
  │  ├─ expected_metric: 预期指标
  │  └─ status: 待办/进行中/完成/已验证
  │
  │ 1:1
  ▼
Review Result（回看结果）
     ┌─ actual_metric: 实际指标
     ├─ delta: 指标变化
     ├─ assessment: 效果评估
     └─ learnings: 经验总结
```

## 八、关键用户旅程

### 旅程一：品牌 NPS 下降的决策闭环

```
Day 1  │ 品牌负责人创建议题："Q3 NPS 下降 5 分，原因是什么？该怎么应对？"
       │
Day 1  │ 系统自动拉取：
       │   • 问卷数据：NPS 各维度得分变化
       │   • 舆情数据：近 3 月社媒口碑趋势
       │   • 竞品信息：竞品同期动作
       │
Day 1  │ 对抗性推理引擎启动：
       │   正方："NPS 下降主因是产品体验，证据：问卷开放题中'卡顿'提及率↑40%"
       │   反方："但舆情数据显示品牌好感度稳定，NPS 下降可能是季节性波动"
       │   裁判："产品体验是主因（置信度 75%），但需排除季节性因素（盲区）"
       │
Day 1  │ 生成决策卡：
       │   建议：优先解决产品卡顿问题
       │   置信度：中高（75%）
       │   盲区：缺少去年同期 NPS 数据做季节性对比
       │   失败预警：如果卡顿是后端问题而非前端，修复周期可能超预期
       │
Day 2  │ 品牌负责人采纳决策卡，系统派生行动项：
       │   ① 产品团队排查卡顿 Top 3 场景（负责人：产品经理，3天内）
       │   ② 补充去年 Q3 NPS 数据做季节性分析（负责人：研究团队，2天内）
       │   ③ 监控竞品下一步动作（负责人：市场团队，持续）
       │
Day 14 │ 行动项完成，录入结果：
       │   卡顿修复后 NPS 回升 3 分，季节性分析确认去年同期无类似下降
       │
Day 14 │ 系统生成回看结果：
       │   决策有效，NPS 回升 60%。经验沉淀：
       │   "当 NPS 下降 + 开放题负面关键词集中时，优先排查产品体验"
```

### MVP 技术简化策略

| 模块 | 简化方案 | 理由 |
|------|---------|------|
| 语义层 NLP | 不单独建，全部用 LLM 在证据入库时一次性处理 | 减少组件复杂度 |
| 向量检索 | 用 Elasticsearch 承载关键词检索 + 语义召回，不单独引入新的向量库 | 减少运维复杂度 |
| 舆情采集 | 对接第三方舆情 API，不自建爬虫 | 法律风险 + 开发成本 |
| 行业报告解析 | 人工上传关键论点摘要，不做 PDF 自动解析 | PDF 解析坑多，MVP 不值得 |
| 音频转写 | MVP 砍掉，只接受文本访谈记录 | 非核心路径 |
| 用户认证 | Supabase Auth | 成熟方案，快速接入 |
| 闭环校正 | 只做状态追踪，不做自动模型校正 | 早期数据量不够 |

### AI 推理引擎调用流程

```
1. 证据入库时：
   Claude API → 实体抽取 + 情感分析 + 主题标签（单次调用）

2. 决策卡生成时（对抗性推理）：
   Step 1: Hybrid RAG 检索相关证据（Elasticsearch 关键词召回 + 语义召回 + LLM rerank）
   Step 2: 正方 Agent 调用（Claude，structured output）  ─┐
   Step 3: 反方 Agent 调用（Claude，structured output）  ─┤ 并行
   Step 4: 裁判 Agent 调用（Claude，综合正反方输出）        ←┘ 串行
   Step 5: 生成决策卡 JSON，存入数据库

   预估成本：~$0.05-0.15 / 次决策（Claude Sonnet）
```

| 第二阶段 | 4 周 | 对抗性推理引擎 + 决策卡生成 + 冲突检测 | 决策卡质量达到可用水平 |
| 第三阶段 | 3 周 | 行动项管理 + 结果回看 | 闭环跑通 |
| 第四阶段 | 3 周 | 3-5 个真实客户试点 | 验证核心假设 |

## 十三、成功指标

### 产品指标

| 指标 | 定义 | MVP 目标 |
|------|------|---------|
| 决策卡采纳率 | 被标记为"已采纳"的决策卡 / 总生成决策卡 | > 40% |
| 行动项完成率 | 已完成行动项 / 总派生行动项 | > 60% |
| 证据复用率 | 被引用超过 1 次的证据 / 总证据数 | > 30% |
| 决策周期缩短 | 使用系统后的平均决策周期 vs 使用前 | 缩短 > 30% |
| 用户周活跃率 | 每周至少登录 1 次的用户 / 总用户 | > 50% |

### 对抗推理质量指标

| 指标 | 定义 | 目标 |
|------|------|------|
| 盲区命中率 | 系统标注的盲区中，用户确认"确实重要"的比例 | > 50% |
| 反方论证有效率 | 反方 Agent 提出的反对意见中，用户认为"有价值"的比例 | > 60% |
| 冲突检测准确率 | 系统标注的证据冲突中，确实存在矛盾的比例 | > 70% |

## 十四、风险与应对

| 风险 | 影响 | 概率 | 应对策略 |
|------|------|------|---------|
| LLM 推理质量不稳定 | 决策卡质量波动大 | 高 | 结构化 prompt + 人工审核兜底 + 持续迭代 prompt |
| 舆情 API 不稳定/限制 | 数据源缺失 | 中 | 预备 2-3 家供应商，支持人工补充 |
| 用户不信任 AI 决策 | 采纳率低 | 中 | 对抗推理增强透明度 + 始终展示证据来源 + 人工可编辑 |
| 数据隐私合规 | 法律风险 | 中 | 数据不出境 + 匿名化处理 + 合规审查 |
| MVP 范围膨胀 | 延期交付 | 高 | 严格 P0/P1/P2 分级，Kill Criteria 机制 |

## 十五、Kill Criteria（停止条件）

如果出现以下情况，暂停项目并重新评估方向：

- 4 周内无法完成第一阶段数据接入
- 对抗推理引擎生成的决策卡，内部评审通过率 < 50%
- 试点用户决策卡采纳率 < 20%
- 用户反馈"不如直接看原始数据"超过 50%
- AI 推理成本超过 ¥5/次决策（商业模式不成立）

## 十六、长期技术护城河

### 领域证据知识图谱 + 决策反馈网络

```
第一阶段（MVP 后 6 个月）— 单客户知识积累
  每个客户积累 Issue → Evidence → Decision → Action → Result 完整链路
  系统可以说："上次类似的 NPS 下降，你们采取了 X 策略，NPS 回升了 Y 点"

第二阶段（1 年后）— 跨客户模式泛化（匿名化）
  证据模式图谱：
    "NPS 下降 + 社媒负面↑ + 竞品新品发布"
        │
        ▼ 历史上 73% 的案例中
        │
    有效决策模式：
        ├── 加速产品迭代（成功率 65%）
        ├── 加大品牌投放（成功率 40%）
        └── 调整定价策略（成功率 55%）
```

这是真正的护城河：
- **数据网络效应**：每个新客户的使用都在增强模式库质量
- **因果链路数据**：不是简单的数据量，而是结构化的"证据→决策→结果"配对
- **竞品无法复制**：即使复制架构，没有这些决策反馈数据就无法提供历史模式推荐
