# ResearchOS 架构设计文档 v1.2

> 本文档只讲技术架构：系统边界、服务拆分、数据模型、AI 推理链路、异步任务、安全与演进。
> 产品设计请见《06-产品设计-v1.2.md》。

---

## 一、设计原则

1. 以"议题→证据→决策→行动→回看"对象链路为核心
2. MVP 采用 Vue 3 SPA + Next.js BFF + 独立 AI 服务，后续按域拆分
3. AI 输出必须可追溯到证据来源，不允许黑盒结论
4. 重任务全部异步化，交互请求保持短链路
5. 安全、审计、可观测性默认内建

## 二、系统边界

### 2.1 系统职责（In Scope）

- 议题管理
- 多源证据接入与标准化
- 证据检索、关联、冲突检测、置信度评估
- AI 对抗性推理与决策卡生成
- 行动项派生与状态追踪
- 回看结果沉淀

### 2.2 上游系统

| 系统 | 交互方式 | 说明 |
|------|---------|------|
| 问卷 SaaS 平台 | REST API 拉取 | 问卷结果 + 开放题文本 |
| 舆情平台 | REST API 拉取 | 社媒帖子 + 情感标签 |
| 文件上传 | HTTP Multipart | 用户手动上传文本/CSV/Excel |
| SSO/身份系统 | OAuth2/OIDC | 企业统一登录 |

### 2.3 下游系统

| 系统 | 交互方式 | 说明 |
|------|---------|------|
| 通知服务 | Webhook/邮件 | 行动项提醒、决策卡就绪通知 |
| 导出服务 | 内部调用 | PDF/PPT 报告生成（P2） |

### 2.4 外部依赖

| 依赖 | 用途 | 备选方案 |
|------|------|---------|
| Claude API | 对抗推理、证据分析、摘要生成 | GPT-4 API |
| Embedding 模型 | 证据向量化 | OpenAI Embedding / 本地模型 |

MVP 共 4 个独立部署单元：
1. Next.js + Node.js 服务（BFF / API 路由 + 实时推送）
2. AI Reasoning Service（推理 + Embedding + 检索编排）
3. Node.js Worker（异步任务）
4. 前端 Vue 3 + TypeScript SPA（静态部署）

## 四、服务拆分

### 4.1 Next.js + Node.js 服务层

| 服务模块 | 职责 | 核心接口 |
|---------|------|---------|
| Issue Service | 议题 CRUD、状态流转、版本管理 | POST/GET/PUT /api/issues |
| Evidence Service | 证据 CRUD、标签、关联、搜索 | POST/GET /api/evidence |
| Decision Service | 决策卡管理、采纳/拒绝、版本 | GET/PUT /api/decisions |
| Action Service | 行动项 CRUD、状态流转 | POST/GET/PUT /api/actions |
| Review Service | 回看结果录入、经验归档 | POST/GET /api/reviews |
| Identity Service | 用户/组织/角色/权限 | /api/auth, /api/users |
| Ingestion Service | 数据源配置、导入任务管理 | POST /api/sources, /api/imports |
| Realtime Service | SSE/WebSocket 推送任务状态与决策卡结果 | /api/events, /api/jobs/:id/stream |

### 4.2 AI Reasoning Service

| 模块 | 职责 | 触发方式 |
|------|------|---------|
| Embedding Pipeline | 文本切片 → Embedding → 写入 Elasticsearch 检索索引 | 证据入库时同步/异步调用 |
| Hybrid Retrieval | Elasticsearch 关键词检索 + 向量检索 + 重排 | 决策卡生成时调用 |
| Adversarial Reasoning | Advocate/Critic/Judge 三角推理 | 决策卡生成时调用 |
| Conflict Detection | 同维度不同来源证据矛盾检测 | 证据入库时异步调用 |
| Confidence Scoring | 多维度置信度评估 | 证据入库 + 决策卡生成 |

### 4.3 Node.js Worker

| 任务类型 | 说明 | 触发方式 |
|---------|------|---------|
| 数据拉取 | 定时从问卷/舆情 API 拉取新数据 | Cron 定时 |
| 证据处理 | 清洗、标准化、标签生成、Embedding | 事件驱动 |
| 冲突检测 | 新证据入库后检测与已有证据的冲突 | 事件驱动 |
| 通知发送 | 行动项到期提醒、决策卡就绪通知 | 事件驱动 + Cron |

## 六、AI 推理链路

### 6.1 总流程

```
用户点击"生成决策卡"
        │
        ▼
┌─────────────────────┐
│ 1. 读取议题上下文     │
│    title + desc +    │
│    domain + 已有证据  │
└─────────┬───────────┘
          │
          ▼
┌─────────────────────┐
│ 2. Hybrid RAG 检索   │
│    ES 关键词检索      │
│    + ES 向量检索      │
│    + 元数据过滤       │
│    → 召回 Top-K 证据  │
│    → LLM Rerank      │
└─────────┬───────────┘
          │
          ▼
┌─────────────────────┐
│ 3. 证据分组           │
│    按维度/主题聚类     │
│    标注 stance        │
│    构建上下文窗口      │
└─────────┬───────────┘
          │
    ┌─────┴─────┐
    ▼           ▼
┌────────┐ ┌────────┐
│4a.正方  │ │4b.反方  │    ← 并行调用
│Advocate│ │Critic  │
└───┬────┘ └───┬────┘
    │          │
    └────┬─────┘
         ▼
┌─────────────────────┐
│ 5. 裁判 Judge        │    ← 串行，依赖 4a+4b
│    综合正反方输出      │
│    评估证据强弱        │
│    识别冲突与盲区      │
│    生成推荐 + 置信度   │
└─────────┬───────────┘
          │
          ▼
┌─────────────────────┐
│ 6. 结构化输出         │
│    生成 DecisionCard  │
```

### 6.2 各 Agent Prompt 设计要点

| Agent | System Prompt 核心指令 | 输出 Schema |
|-------|----------------------|-------------|
| Advocate | 你是正方辩手。从提供的证据中构建支持该议题方向的最强论证。每条论据必须引用具体证据 ID。评估每条论据的强度（强/中/弱）。 | `{arguments: [{claim, evidence_ids, strength, reasoning}]}` |
| Critic | 你是反方辩手。主动寻找反驳证据、识别逻辑漏洞、质疑数据质量和样本偏差。指出正方可能忽略的风险。 | `{rebuttals: [{claim, evidence_ids, strength, reasoning}], data_quality_issues: [...]}` |
| Judge | 你是裁判。综合正反双方论证，评估证据强弱。输出：推荐方向、冲突点、信息盲区、前提假设、失败预警、置信度评分及理由。 | `{recommendation, conflicts, blind_spots, assumptions, failure_warnings, confidence_score, confidence_reason}` |

### 6.3 RAG 检索策略

```
召回阶段：
  1. Elasticsearch 关键词检索（BM25）→ Top 50
  2. Elasticsearch 向量检索（dense_vector similarity）→ Top 50
  3. 合并去重 → ~60-80 条候选

过滤阶段：
  - 按 tenant_id 隔离
  - 按 freshness 过滤过期证据
  - 按 source_type 保证多源覆盖

重排阶段（LLM Rerank）：
  - 输入：议题描述 + 候选证据摘要
  - 输出：相关性排序 Top 20
  - 优先保证：时效性 > 来源质量 > 语义相关性

上下文构建：
  - 保留原始引用片段 + source_ref
  - 按维度/主题分组
  - 总 token 控制在模型上下文窗口 60% 以内
```

### 6.4 置信度评估模型

```
confidence_score = weighted_avg(
  source_quality   × 0.25,   // 来源可信度（权威期刊 > 社媒帖子）
  sample_size      × 0.20,   // 样本量（2000份问卷 > 50条评论）
  freshness        × 0.15,   // 时效性（1周内 > 3个月前）
  consistency      × 0.20,   // 多源一致性（多个来源结论一致 → 高）
  coverage         × 0.10,   // 维度覆盖度（覆盖多个维度 → 高）
  conflict_level   × 0.10    // 冲突程度（冲突越多 → 越低）
)

输出：
  score: 0-100
  level: "高" (≥75) | "中" (50-74) | "低" (<50)
  reason_codes: ["来源可靠", "样本充足", "存在冲突", ...]
```

### 6.5 失败兜底

| 场景 | 兜底策略 |
|------|---------|
| LLM 调用超时/失败 | 回退为"证据摘要模式"，不输出对抗推理结论 |
| 检索证据不足（<3条） | 标注"证据不足"，建议用户补充数据源 |
| 上下文超长 | 分批聚合：先按维度分组推理，再汇总裁决 |
| 正反方输出格式异常 | JSON Schema 校验 + 重试 1 次，仍失败则降级 |

## 七、异步任务设计

### 7.1 任务分类与优先级

| 类型 | 任务 | 优先级 | 超时 | 重试 |
|------|------|--------|------|------|
| 接入 | 问卷数据拉取 | 中 | 60s | 3次 |
| 接入 | 舆情数据拉取 | 中 | 60s | 3次 |
| 处理 | 证据清洗+标签 | 中 | 30s | 2次 |
| 处理 | Embedding 生成与 ES 索引写入 | 中 | 30s | 2次 |
| 推理 | 冲突检测 | 低 | 60s | 1次 |
| 推理 | 决策卡生成 | 高 | 120s | 2次 |
| 通知 | 行动项到期提醒 | 低 | 10s | 3次 |

### 7.2 任务流水线

```
数据源同步触发
    │
    ▼
[拉取原始数据] → 原始文件存入对象存储
    │
    ▼
[清洗+标准化] → 写入 TiDB evidence
    │
    ├──▶ [Embedding 生成] → 写入 Elasticsearch evidence_index
    │
    ├──▶ [自动关联] → 写入 TiDB issue_evidence
    │
    └──▶ [冲突检测] → 更新冲突标记 / 决策上下文
```

### 7.3 幂等与补偿

- Import Job 以 `source_ref` 做唯一约束，重复拉取不会产生重复证据
- Worker 消费幂等：同一 task_id 重复执行结果一致
- 失败超过重试上限 → 进入死信队列 → 管理后台可查看和手动重试

## 八、安全设计

### 8.1 认证与授权

```
认证方式：
  - 邮箱+密码登录（MVP）
  - 企业 SSO / OAuth2（P1）
  - API Token（P2）

令牌机制：
  - Access Token: JWT, 15 分钟有效
  - Refresh Token: 7 天有效, 单次使用

权限模型（RBAC）：
  - admin: 全部权限 + 团队管理 + 数据源配置
  - member: 议题/证据/决策卡/行动项的读写
  - viewer: 只读（P2）
```

### 8.2 多租户隔离

- 应用层：所有查询强制附加 `tenant_id` 条件
- 数据层：核心表均含 `tenant_id` 字段 + 索引
- 对象存储：路径按 `/{tenant_id}/` 隔离

### 8.3 数据安全

| 层面 | 措施 |
|------|------|
| 传输 | 全链路 TLS |
| 存储 | 数据库加密、对象存储加密 |
| 密钥 | 第三方 API Key 使用密钥管理服务，不落代码 |
| 脱敏 | 日志中不记录证据原文，仅记录 ID |

### 8.4 AI 安全

| 风险 | 防护 |
|------|------|
| Prompt 注入 | 用户输入与系统 prompt 严格隔离，证据内容做清洗 |
| 幻觉输出 | 所有论断必须绑定 evidence_id，无引用的结论标记为"AI 推测" |
| 输出校验 | JSON Schema 强校验，不合格输出不落库 |

## 十一、关键架构决策记录（ADR）

### ADR-01: Next.js BFF + 独立 AI 服务 vs 全部逻辑集中在单一 Node 进程

- 决策：MVP 采用 Next.js + Node.js 作为主业务入口，AI 推理能力保持独立服务
- 理由：Next.js 适合承载页面/API/BFF 能力，AI 推理链路与检索编排仍需要独立扩缩容和资源隔离
- 后果：系统仍然不是纯单体，但前后端主干技术统一为 Node.js 生态，后续可按域继续拆分

### ADR-02: TiDB + Elasticsearch vs 单库承载事务与检索

- 决策：结构化主数据存储在 TiDB，全文/向量检索由 Elasticsearch 承载
- 理由：TiDB 负责事务一致性、扩展性和多租户主数据；Elasticsearch 更适合关键词召回、过滤和混合检索场景
- 后果：需要维护 TiDB → Elasticsearch 的索引同步链路，但换来更清晰的数据职责边界

### ADR-03: 三角推理 vs 单次总结

- 决策：Advocate/Critic/Judge 三角推理
- 理由：单次总结倾向给出单一结论，无法暴露冲突和盲区；三角推理是核心产品差异化
- 后果：每次决策卡生成需要 3 次 LLM 调用，成本约 ¥0.3-1.0/次

### ADR-04: 异步化重任务

- 决策：数据导入、Embedding、决策卡生成全部异步
- 理由：这些任务耗时 10s-120s，同步调用会阻塞用户交互
- 后果：需要 SSE/WebSocket 推送结果，前端需要处理异步状态

### ADR-05: AI 输出必须绑定证据引用

- 决策：所有 AI 论断必须关联 evidence_id
- 理由：防止幻觉，增强用户信任，满足审计需求
- 后果：prompt 设计更复杂，输出 token 更多，但这是产品核心价值
